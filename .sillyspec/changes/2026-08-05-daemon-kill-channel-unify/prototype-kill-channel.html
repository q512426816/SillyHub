daemon kill 通道统一 · 方案 C（分层渐进）

让"终止"在所有场景可靠落地：Claude/Codex interactive · batch lease · budget 超限 · 终态可见性

① 当前断点（4 个隐患）

# backend→WS 信号层已修好（2026-07），但"daemon 物理杀进程"层断了

P0 Claude END   只发 stdin EOF，没调 query.close() → 卡死 turn 时进程不退，持续烧 token
P1 Codex END   sessionManager 不主动调 _close() → 要等当前 turn 自然结束才杀
P2 Batch kill  只靠 HTTP 心跳轮询感知 cancelled → 有一个心跳周期延迟
P1 Budget      daemon 连 budget 字段都没收到，零运行期检查点，烧穿预算

② 方案 C：修复后的 kill 收敛链

# INTERRUPT 仍软中断（续轮），只有 END/fail/budget 才硬杀（D-001）

前端 [结束会话]
  └─▶ backend end_session ─标记 ended + terminating_at─▶ WS SESSION_END
                                                            │
                              daemon sessionManager.end() ◀─┘
                                └─ _terminateSession(state)  # 新私有收敛函数
                                     ├─ driverHandle.close?.()   # Claude=query.close() Codex=_close()
                                     │    └─ SDK: stdin EOF → 2s → SIGTERM → 5s → SIGKILL  ✅ 真能杀
                                     └─ inputQueue.close()
                                            │
                              daemon 收口 ◀─┘
                                └─ notifySessionEnd(ended) ─清 terminating_at─▶ backend  # ACK

batch:  cancel_lease ─WS LEASE_CANCEL─▶ daemon taskRunner.cancel() ─▶ _killChild SIGTERM/SIGKILL  (即时, 不等心跳)
budget: 执行循环累计 token ≥ budget_tokens ─▶ 软切断 flag（当前 turn 跑完不续轮）+ 回传 budget_exceeded
Windows：进程 kill 全交给 SDK close()（win32: stdin.end + 5s TerminateProcess），daemon 不自己 taskkill（守已知陷阱）

③ 终态状态机（轻量 ACK，落地 multica"执行端确认"）

running
  │ cancel/end
  ▼
terminating  (terminating_at = now)
  │
  ├─ daemon 回 ACK(≤30s) ─▶ terminated (清 terminating_at)
  │
  └─ 超时 30s 无 ACK ─▶ terminate_timeout (告警, 不阻塞)

# 与方案 B 的区别：
# - 不引入 outbox 重试（复杂）
# - 不改终态中间态状态机（不动 PPM 已上线）
# - 只加一个时间戳 + 复用现有上报 + 超时告警
# 拿到"执行端确认"可见性，风险中低

④ 实施波次（概览，详见后续 plan）
