## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

v1 的两大问题分别对症：**卡顿**——渲染循环逐帧 shadowBlur/全屏 overlay 颗粒/每帧重建渐变，v2 引擎重写为「静态层缓存 + 辉光精灵贴图 + 隔帧颗粒 + 自适应画质三档」的性能优先架构；**内容不符**——v2 从抽象图示转向真实产品演示：用浏览器自动化登录线上环境（crrcdt.ppdmq.top）采集 28 张真实界面截图入库 `docs/promo/v2/assets/`，影片每幕以截图为主角（带地址栏的浏览器窗口框 + Ken Burns 缓推 + 圆角高亮标注 + 人话字幕），按 11 幕约 300 秒讲完整平台故事；配乐沿用 WebAudio 合成并扩展至约 120 小节分章情绪。v1 文件保留，`docs/promo/README.md` 指向 v2 为正片。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无平台接口变化：不改 backend/frontend/daemon 代码。新增静态交付面：`docs/promo/v2/index.html`（入口）+ `docs/promo/v2/assets/*.jpg`（28 张截图，命名即语义）+ 更新 `docs/promo/README.md`。页面内部约定：`window.__promoFilm` 调试句柄（play/pause/seek/fps 采样），不承诺跨页契约。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   成立。画面仍是主时钟 T 的确定性函数（截图 Ken Burns 参数、高亮时窗、字幕均由 T 解析计算）；用户输入只有播放/暂停/seek，seek 任意跳转画面与配乐精确对齐；图片加载为渐进增强——未加载完成时该幕显示窗口框+URL 条骨架，不阻塞时间轴。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   不适用：纯静态页面，无后端无存储；单标签页单 rAF 循环串行绘制；多开标签页各自独立。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全。标签页隐藏自动暂停（visibilitychange）；AudioContext 仅用户手势后创建、suspend/resume 管理生命周期；图片缓存进程内共享（Image 对象池），无持久状态。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会。零网络请求（截图为本地相对路径资源）、无 localStorage；画质档位仅内存态。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：①截图内含真实业务信息（内网 Git 地址、成员姓名）——已按用户提供的环境授权采集，影片内嵌说明「界面来自真实运行中的 SillyHub」；如需脱敏版后续可换资产重跑。②28 张图约 3.5MB，首帧前需预解码——用「首屏渐进 + 按幕预取」策略（当前幕及下一幕图片优先解码），海报页停留期预热全部资产，点击播放时资源已就绪。③5 分钟单页 rAF 长跑内存——所有节点按幕创建/销毁，无无限增长的 livePads/定时器（音乐节点按小节自带终止）。
放弃的方案：①录屏视频嵌入（webm）——体积失控且违背纯代码拍片思路；②iframe 嵌线上环境实况——需要账号态且播放不可控（seek 无法重现），改为确定性截图 + 标注动画；③继续 v1 引擎修补——shadowBlur 散布各幕，修不干净，重写引擎成本低于维护。
