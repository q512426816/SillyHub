# 提案书（Proposal）

## 动机

用户在 Web 会话发送消息后，响应慢时（新会话首轮冷启动实测最长约 40 秒）页面只有笼统的「执行中 + 思考中」，无法区分系统在启动 AI 进程、同步规范文件还是已经卡死。链路调研证实三类「零信号盲区」（消息转发段 / 启动准备段 / 首响间隙）——执行器内部甚至已有完善的分步计时日志，只是从未上报给页面。本变更把这些已有数据「顺便」发出来，让等待过程可见。

## 关键问题

1. **盲区无信号**：消息从网页到 AI 开始响应之间，转发段（backend 状态机仅落库不上前端）、启动准备段（daemon 分步日志仅本地）、首响间隙（inject 到首个 AI 事件）三段完全没有面向前端的事件，前端只能显示兜底文案「思考中」。
2. **异常不可分辨**：执行器离线、消息投递失败、阶段卡超时与「正常慢」在页面上表现完全相同，用户无从判断该等还是该查。
3. **改造基建已在**：`agent_session:{id}` SSE 事件通道、daemon→backend HTTP 上报模式（notify_bash_status 系）、控制指令状态机翻转点全部现成，缺的只是阶段事件的定义与接线。

## 变更范围

跨 backend / sillyhub-daemon / frontend 三端（20 个文件，见 design.md 文件变更清单）：

1. 新增 SSE 事件 `turn_phase` 与 9 值阶段词表（三端共同契约）；
2. backend：新增 turn-phase 上报端点 + 发布 helper + 控制指令状态机翻转点直接发布 `dispatched`/`delivered`（零 daemon 依赖）；
3. daemon：启动各步骤边界 + inject 注入点 + 首事件点上报（失败静默不阻塞主流程）；
4. frontend：状态条阶段文案映射（替代笼统「排队中/执行中」）+ 单阶段停留 ≥30s 警示样式 + 「已等待 N 秒」；
5. 原型已产出并经用户确认（`prototype-session-stage-progress.html`，真码管线产物）。

## 不在范围内（显式清单）

- 不做阶段轨迹历史回看/持久化（轻量单行形态，D-001）；
- 不做异常告警系统（弹窗/通知/告警面板）——超时仅状态条变色（D-003）；
- 不新增 daemon↔backend WS 消息类型（D-004）；
- 不改 SSE 透传层、不改既有事件语义、不改任何表结构（零 migration）；
- 不做服务端超时阈值配置项（前端常量 30s，D-007）；
- 不覆盖子代理目录、群聊 typing 等旁路展示位（首版仅主轮状态条）。

## 成功标准（可验证）

- 新会话首轮发消息后，状态条依次显示「已发送 · 等待执行器领取 → 执行器已接收 → 正在准备技能环境 → 正在同步规范文件 → 正在加载工具配置 → 正在启动 AI 进程 → 已就绪 · 等待 AI 响应 → AI 开始响应」，随后活动摘要接管（原型 ② 区形态）。
- 追问轮显示「已发送 → 执行器已接收 → 消息已送达 AI → AI 开始响应」（原型 ③ 区形态）。
- 任一阶段停留 ≥30s 时状态条切警示样式并显示「已等待 N 秒」（原型 ④ 区形态）。
- 无 phase 信号的轮（老版本 daemon / 上报失败 / 断线重连后）状态条与现状展示完全一致——聚焦测试断言现状文案分支零改动。
- daemon 上报路径注入失败（模拟网络错误）时会话创建/注入主流程不受影响（daemon 聚焦测试断言不抛出）。
- backend turn-phase 端点：无凭据 401、跨会话上报 404、正常上报 200 且 Redis 收到 `turn_phase` 事件（backend 聚焦测试断言）。
- `pnpm gen:types`（frontend）与 `pnpm -C sillyhub-daemon gen:types` 在同一变更内跑过并提交两处 api-types（仓库规则 21）。
