# 设计记录（Design Record）— 2026-10-23-marquee-thinking-fulltext

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

thinking 条目此前与其他类型共用 `clip()`（折叠空白 + 64 字截断），只滚动一个短摘要。改为：

1. 新增 `normalizeText()`（只折叠空白、不截断）；thinking 分支使用它，保留完整思考文本；
2. `MarqueeItemView` 用组件内 rAF 驱动**一次性单向滚动**（不再用 CSS 无限动画）：
   - 终点 `marqueeTickerEnd(textWidth, viewWidth) = min(0, viewWidth - textWidth)`——文本末尾贴住窗口右缘；
   - 从开头滚到终点即停，**不复制内容、不循环**；
   - 文本流式增长时，`entry.text` 变化 / ResizeObserver 更新终点，滚动继续跟随新末尾；
   - 落后距离越大速度越快（220~900px/s），避免追不上流式输出；到达当前末尾后停排，文本再增长时重启；
3. 完成态仍走单份 `truncate`（回到开头）+ 耗时，不滚动；其他类型条目继续使用 `clip()` 的既有摘要截断。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- 新增内部函数 `normalizeText(text): string`（不导出）。
- 新增导出纯函数 `marqueeTickerEnd(textWidth, viewWidth): number`。
- thinking 条目的 `text` 长度不再受 64 字限制；其他类型不变。
- `MarqueeItemView` 内部用 rAF 写 `transform`，一次滚到当前末尾；CSS 类
  `.sh-live-marquee-ticker` 不再包含 animation（仅作标记与合成提示）。
- 组件 props / 其余导出 / 后端接口：**无变化**。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   - 成立。文本长度只影响动画时长，与事件顺序无关；全文内容来自当前段快照。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   - 无写面；纯展示。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   - 安全。ticker 动画随元素卸载/状态切换自然停止；reduced-motion 仍静态截断；窗口最多 12 条，全文 DOM 有界。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   - 不涉及数据；每个条目独立。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：极长思考滚动时间较长；但跑马灯定位是感知，正文区有完整思考可读，窗口仅 12 条、DOM 文本量可控。
- 流式增长时文本宽度测量依赖 ResizeObserver / 文本变化 effect；浏览器布局稳定时跟随连续，极端情况下可能有一次轻微追赶。
- 速度按文字宽度与距离自适应（220~900px/s）：流式爆发时能跟上，稀疏时慢速流动。
- 放弃方案：① 保留 64 字截断（用户明确要全文）；② CSS 无限循环动画（用户明确禁止循环）；③ 到达末尾直接停住不跟随（思考仍在流式增长时会被落在旧位置，用户明确要求跟随）。
