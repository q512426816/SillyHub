# 设计记录（Design Record）— 2026-10-28-session-list-loadmore-fetch

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

对 2026-10-28-session-list-refresh-and-paging 的两处设计错误返工（用户实证
反馈：「点击怎么都没触发后端接口」「显示还有 28 条，点击只加载 1 条变还有
27 条」），改动收敛在 session-list-panel.tsx：

1. **递增计数语义改「跳过已显示」**：visibleGroupSessionsWithExtra 从
   「head=10+extra ∪ 在线全显」改为 filter 预算计数——默认展示（前 10 ∪
   在线全显）之外的条目按服务端序给 extra 个预算，每点一次 +20 恰好新增
   20 条**此前未显示**的行（原实现 head 扩 20 的位置被默认已显示的在线
   条目占据，净增可能只有 1——「还有 28→还有 27」实证根因）。
2. **点击即触网**：组内「加载更多」点击时若服务端总数 > 已加载数，立即调
   loadMoreSessions（相同筛选参 offset 续拉，**每次 20 条**，续拉步长从
   500 收敛为 20——用户拍板「每次点击加载更多在无限加载每次 20 条」）；
   树底部入口同一函数。首屏仍 limit=500 一次拉（树分组基础不动）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- 后端/端点：无改动（既有 limit/offset 真分页直接消费）。
- visibleGroupSessionsWithExtra（导出纯函数）：语义变更如上；extra=0 输出与
  defaultVisibleGroupSessions 逐字节一致（默认态零漂移）。
- SESSION_EXTRA_PAGE_LIMIT → EXTRA_PAGE_LIMIT = 20（每次续拉条数）。
- 组件对外 props 无变化；组内「加载更多」按钮行为增强（本地展开 + 条件
  并行触网）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   offset 翻页排序漂移维持 id 去重兜底（上一变更既有）；触网响应晚于用户
   再点（extra 已再 +20）时数据照常 append——展示层（递增计数）与数据层
   （续拉）解耦，互不阻塞。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   extraLoading in-flight 守卫防双拉；本地展开 state 与续拉 state 独立，
   连点安全（展开立即可见 + 触网被守卫合并）。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   筛选/scope/视图切换重置语义不变（组内递增清零 + 附加段清空）；续拉在途
   时切换视图，附加段被重置 effect 清空、迟到响应经 setState 函数式 append
   到空数组（该新口径下次进入仍从空附加段起步）——极端窗口多出的条目会被
   id 去重与口径过滤兜住，不丢行不串台。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   续拉携带与首屏相同筛选参（listParamsBase 单一来源），不串台。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：组内点击触网拉回的 20 条可能不属于该组（进其它组），该组本次点击
只见本地展开的行——与「无限加载」心智一致（列表整体在生长、按钮可重点），
可接受。放弃的方案：组内按钮完全等价树底部入口（点击只触网不本地展开，等
响应回来组内才多行）——本地明明还有隐藏行却等网络，慢且浪费；选「本地展开
+ 并行触网」组合。
