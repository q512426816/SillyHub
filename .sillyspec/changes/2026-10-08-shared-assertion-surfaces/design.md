# 设计记录（Design Record）— 2026-10-08-shared-assertion-surfaces

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

两轮 CI 清偿复盘：14 个失败用例中 9 个同模式——生产契约变更只更新了本变更内测试，漏了散落在其它文件钉住同一契约的断言（六面：迁移链尾锚/daemon 心跳参长/前端 TABS 数量/caps 全对象/previewers 枚举 mock/backend 词表对账正则）。方案是把这些「共享断言面」显性登记：①knowledge/testing-gotchas.md 新增条目逐面登记（契约源→钉子测试→动作），INDEX.md 挂关键词索引——flow start 知识注入与子代理 INDEX 查询可命中，这是工具链原生提醒通道；②五个契约源码处加一行同步提醒注释（schema.py/daemon.ts/workspace-tabs.tsx/provider-caps.ts/previewers/index.ts），动手改契约的人当场可见。选注释+知识库而非自动生成清单脚本：登记一次成本低、命中面即改契约现场与 flow start 两处，自动方案（AST 扫描钉子）复杂度不成比例。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：清单自身腐化（新增共享断言面不登记、钉子测试移动不更新条目）——缓解：条目末尾写明「新面按同款登记」的口径，且知识条目进 distill 链可被后续 knowledge 命令校验。放弃方案：CI 内自动扫描钉子断言生成清单（AST/grep 解析 toHaveLength/toEqual 钉子反查契约）——跨语言三端解析成本高且误报难消，先人工登记验证命中价值再谈自动化。
