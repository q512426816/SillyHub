# 提案书（Proposal）— 变更中心会话驱动化

## 动机

变更中心的现有模型把平台做成了「流程发动机」：表单创建变更、详情页控制台推进阶段、会话只是配角。但真实的使用方式是——用户跟 agent 对话、agent 靠本地 sillyspec 技能自己走流程。模型与实际倒挂，导致：用户要在平台表单里复述一遍需求、在详情页手动推进本该 agent 自己走的阶段、会话入口藏在变更里用不顺手。本次把模型翻转过来：**会话是第一步入口，平台只做展示 + 会话入口 + 关键节点人工审批**。

## 关键问题

1. **创建入口错位**：变更只能从「+ 新建变更」表单创建，而 agent 明明能在会话里用本地 sillyspec 命令建变更——且调研证实这条路的变更**根本到不了平台列表**（增量同步不触发重扫描，变更落盘但 `ux_changes` 无行）。这是数据链路断点，不是 UI 问题。
2. **平台越位管执行**：详情页的推进阶段/重新派发/团队配置/选档案都是执行控制，本该由 agent 在会话里自主推进；用户被迫当「人肉下一步按钮」。
3. **审批后体验断裂**：审批通过后平台自动派发 agent（执行控制残留），且用户若走会话驱动，审批结果要自己回会话传话。

## 变更范围

- 后端：daemon 增量同步带 `change_dirs` 标注 + backend 兜底检测触发 scoped 重扫描（零删除守卫）；reparse 新变更自动绑定最近活跃会话（新表 `change_session_links`）；审批四端点改为只落状态 + 投影收敛 + 后端服务身份注入绑定会话；删除 change_writer create/proxy-create/execute/documents 端点；扩展 agent-sessions 列表端点。
- 前端：工作区独立「会话」页（复用交互式会话面板，workspace 级）；变更中心去表单（空态引导会话）；详情页去全部执行控制（含 quick 分支），审批卡改「通过/打回并通知绑定会话」+ 三类降级提示。
- 文档 + 测试（backend pytest + frontend vitest）。

## 不在范围内（显式清单）

- 不改 sillyspec 工具本身（CLI/MCP 配置协议）。
- 不新增 `create_change` MCP 工具。
- 不动 daemon 调度/lease/mission/kill 机制。
- 不做会话内审批 UI（审批入口留在变更详情页）。
- 不做旧数据迁移/历史兼容（未上线允许清数据）。
- 不做绑定会话的手动改绑/显式绑定工具（V1 自动绑定，绑偏为已知边界）。

## 成功标准（可验证）

- 会话里 agent 执行 `sillyspec` 新建变更 → 增量同步后变更**自动**出现在平台变更中心列表（无需手动重扫描；新旧 daemon 均可）。
- scoped 重扫描绝不删除范围外变更（测试覆盖零删除语义）。
- 变更中心无任何「新建变更」入口；工作区有一级「会话」tab 可发起/回看会话。
- 变更详情页无任何执行控制按钮；审批通过/打回后：状态落库、投影立即收敛、绑定会话收到注入消息；agent 忙/会话结束/注入异常三类降级不回滚审批。
- 全量 pytest + vitest 通过。
