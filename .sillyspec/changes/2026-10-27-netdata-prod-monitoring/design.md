# 设计记录（Design Record）— 2026-10-27-netdata-prod-monitoring

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

答：在生产服务器（124.222.127.242，Ubuntu 24.04，4 核 / 7.5G 内存 / 59G 盘用 30%）宿主机上用官方 kickstart 脚本安装 Netdata（`--stable-channel` 锁稳定通道、`--disable-telemetry` 关遥测上报），装完立即改 `/etc/netdata/netdata.conf` 的 `[web] bind to` 为 `127.0.0.1` 并重启服务——面板本身无密码认证，回环绑定 + SSH 隧道是唯一访问面，即使将来安全组误放行 19999 也不暴露。选 Netdata 而非 Prometheus+Grafana：目标是「出事后还原秒级现场」（瞬时抖动/OOM/单容器打满），单机零配置开箱即用；长期容量趋势腾讯云自带云监控已覆盖，不重复建设。容器级排查价值：生产栈五个容器（backend/frontend/postgres/redis/minio）以 docker compose 运行，Netdata 经 cgroups 自动按容器分指标，无需任何配置。仓库侧唯一改动是 deploy.md 模块卡补一条运维排查条目。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

答：无代码接口变化。新增对外可见面：① 服务器宿主层新增 systemd 服务 `netdata`（开机自启，监听 `127.0.0.1:19999`，不占 compose 栈端口、不进 compose 网络）；② `deploy.md`「注意事项」节新增一条生产监控条目（文档内容，非代码）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   答：不适用——无事件流/输入序问题；kickstart 安装为幂等操作，中断后重跑自断点续装，不产生半装状态。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   答：`/etc/netdata/netdata.conf` 仅本变更修改（服务器当前无 netdata 残留，安装与配置在同一次 SSH 会话内完成）；与其它会话的部署操作（load-and-up.sh 只动 compose 栈）无共享写面。仓库侧 deploy.md 为共享文档，Edit 前按惯例重读最新态。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   答：Netdata 为 systemd 服务，崩溃自愈由 systemd 接管；服务器重启后随开机自启恢复。数据默认落本机分层存储，卸载（官方卸载脚本或包管理器）不影响 compose 栈任何数据卷。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   答：仅 124.222.127.242 单机，不接入 Netdata Cloud（指标数据不出网）；对 compose 栈只读采集（cgroups/proc），不改容器行为；多实例不涉及。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

答：最大风险是公网暴露——Netdata 面板无认证，若监听公网网卡且安全组放行即等于把全机指标公开。对策双保险：① 服务端只绑 127.0.0.1（应用层兜底，配置错误也不出网）；② 验收时从办公网实测 19999 不可达。次级风险：资源占用——官方口径约 1~5% 单核 + 100~400MB 内存，服务器余量 5.9G 内存，可接受；磁盘默认分层库上限约 1~2G，盘余 41G，可接受。试过但放弃的方案：① apt 装 Ubuntu 仓库版（v1.44 老旧，UI/容器插件弱于 stable 通道现版）；② Netdata Cloud 云端汇总（指标出网，与自托管诉求冲突）；③ 安全组放行 19999 限源 IP（家宽出口 IP 漂移，维护成本高且误配置即暴露，不如 SSH 隧道零暴露）；④ Prometheus+Grafana（运维成本高，单机秒级现场场景过重）。
