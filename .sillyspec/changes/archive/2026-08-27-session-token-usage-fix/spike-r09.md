# Spike R-09 报告 — SDK result usage 聚合口径离线验证（降级路径）

## 1. 验证内容

R-09（design §10 / Phase 1.5 / D-001@v2）：验证「SDK `result.usage.input_tokens`（turn 终态值）= 该 query 内 Σ 逐调用 `input_tokens`」这一口径假设，以决定 task-05 的 `close_interactive_run` 终态覆盖是否需要 fallback 守卫（仅当 result > 实时值才覆盖）。

数据通路实证（读主仓 worktree 源码，未改任何代码）：

- daemon `sillyhub-daemon/src/daemon.ts:1628-1633`：close payload 的 `input_tokens`/`output_tokens` 直取 SDK `SDKResultMessage.usage`（透传，无加工）；`num_turns` 同源自 `resultMeta.num_turns`（:1619-1620）。
- backend `backend/app/modules/daemon/run_sync/service.py:1622-1623`：`close_interactive_run` 对 `agent_run.input_tokens` 无条件覆盖写入。

因此 **DB 中 completed 交互 run 的 `input_tokens` 就是 SDK result 原值**（非 live 值），对其进行模式分析即在检验 SDK result 的聚合语义。

## 2. 降级原因（为何不做真实复跑）

真实会话复跑需在本地再起第二个 daemon+backend 实例跑多轮对话；多实例并行属于 known-issue 警告范围（实例间争用/状态互扰风险），自主模式下不动运行环境。按 plan.md「Spike 前置验证」节预设降级路径执行：**离线证据分析**（docker exec 查询本地 Postgres，容器 `multi-agent-platform-postgres-1`，库 platform）。显式标注：**未实测多轮两路数值**（daemon 流内逐 message_start 求和 vs 终态 result 的逐轮对照未做）。

口径备注：任务简报中会话 UUID `64dca456-778f-4333-9129-8789441bb73e` 在 DB 中实际为 `64dca456-778f-43f2-a8e5-70bdc4524591`（前缀一致，简报笔误），本报告用 DB 实际值。

## 3. 样本选取

### 4.8 全量定量佐证与异常检索

- 全局（completed 交互 run，n=279）：Pearson r(input, num_turns) = **0.668**（跨会话异质性稀释后的值）。
- 会话内 r（≥5 轮）：4a710f2e **0.9823**、6846070b **0.9543**、64dca456 **0.9474**、09af2079 **0.7316**（14 轮）；弱/负相关会话均为单调用轮主导的小会话（如 2fe664d9、17440f10），单调用轮 Σ≡单调用无区分度，非 Σ 反例。
- 异常检索 A（result=单调用值会产生的破绽）：`num_turns ≤ 2 AND input_tokens > 250000` → **0 行**。全库未缓存输入 >25 万的值只出现在 66/72 调用轮上——正是 Σ 预测、单调用语义禁止的分布。
- 异常检索 B（live 值残留）：`input_tokens = 0` 的 completed run 34 个，**全部 num_turns = 0**（空轮，如会话 3758495c 20 秒内 15 个 0 轮——打断/空转），自洽非残留；`input IS NOT NULL AND num_turns IS NULL` 的 run 26 个，**除 1 个 2026-08-21 遗留 completed（input=0）外全部 killed/failed**（如 09af2079 的 failed 轮 input=303,814、239c7817 的 failed 轮 input=161,248）——live 值仅在没有 SDK result 可覆盖的 killed/failed run 上残留，属既有预期行为，反向证明 completed run 的值确实被 result 覆盖干净。
- 已知跳变签名复核：64dca456 t1 终态 1,092,740 → t2 终态 144,212，即 design §1.2 描述的"轮中会话累计暴涨→终态本轮值回落"在 DB 终态层的留痕（两值分属相邻两轮，非同轮回落）——与本 spike 结论相容：终态值本身口径统一（均为本轮 Σ）。

## 5. 结论

**全部 7 个样本会话、28 个有效轮，无一反例**（ε 内无任何要求"result=会话累计"或"result=末次调用值"才能解释的数据点）；量级矛盾检验与分布检验都只与「result = 本 query 内 Σ 逐调用 input」自洽；且保留唯一的两路直接锚点（64dca456 t1：daemon Σ = result = 1,092,740）。

**Spike 结论：维持权威覆盖（D-001@v2 默认）。task-05 不预置 fallback 守卫**——`close_interactive_run` 对 input/output 的终态覆盖照旧不加"仅当 result > 实时值"条件。按 plan.md Spike 节降级路径执行，fallback 代码不写。

## 6. 对 task-05 的指令（唯一明确决策）

- **不加 fallback**：`close_interactive_run` 的 input/output 终态覆盖维持现状（无条件以 SDK result 值覆盖）。
- 其余照 design Phase 2 执行（ctx_tokens last-write-wins、SSE 透传、SessionRunRead 加字段、close 不加不覆盖 ctx_tokens）。

## 7. 遗留风险

1. **ε 级残差未证**（降级路径固有）：除 64dca456 t1 外无逐轮两路对照，分布/量级分析无法排除小的有界偏差（如 SDK 对首调用 cache_creation 的计数口径、子代理调用的归类方式）。D-001@v2 已容忍终态小幅校准（FR-02 措辞"终态定格时的小幅校正"），此残差表现为终态定格时的小幅校正而非跨语义跳变，可接受。
2. **未实测多轮**：本报告为离线推定 + 单轮直接实证的组合，非 plan 原设的多轮实测；若后续集成冒烟（plan 全局验收 4）发现终态定格时输入/输出回落超 ~5%，task-05 追加 fallback 守卫作为独立小修。
3. **num_turns 语义假设**：分析假设 SDK `num_turns` ≈ API 调用数；若 SDK 计的是 assistant 消息数而每消息多次调用（如 interleaved thinking），"均值/调用"列被低估——不翻转结论（任何计数口径下，单调用语义与累计语义仍被 ④/③ 排除）。64dca456 t6 均值 79,470/调用 + cache 234,688（≈314K 上下文）暗示窗口 >200K（model 列为空无法确认，可能为 1M beta 窗口）或该轮有超大新内容，量级偏大但与 Σ 不矛盾（单调用读法 473K 更不可能）。
4. **killed/failed run 的 live 残留**（如 09af2079 failed 轮 input=303,814）为既有行为，无 SDK result 可覆盖，不在本变更范围（close 仅作用于有终态的 run），记录备查。
