# 决策记录（Decisions）— 2026-10-20-session-status-live-sync

## D-001@v1: 设计期风险与放弃方案（底稿）
- 类型：process
- 状态：confirmed
- 答案：最大风险：信号频率放大列表查询负载——每个 run 生命周期新增约 3~5 个信号（创建/激活/审批对/终态），每个信号触发一次列表 refetch（limit=500 窗口函数查询）。评估：10s 轮询本来就执行同款查询，事件驱动只是把「定时查」变「变化时查」，稳态总频率不升反降；且 400ms 去抖把轮内密集信号合并。若极端高频会话（自动化连续注入）仍显负载，后续可加信号侧节流（不在本变更范围）。 试过但放弃的方案： - 前端 turn_started/全事件扇出 onSessionListRefresh——只覆盖当前打开的会话，其他会话（列表里未打开的）状态变化仍瞎；且每轮多次 invalidate 无谓压力。放弃，改为后端信号根治（覆盖全部会话）+ 仅审批边沿本地兜底。 - 列表轮询间隔调小（10s→2s）——治标：全静默 30s 退化和「变化时查」语义都没解决，纯增加空转查询。放弃。 - 把 current_run_status 塞进 per-session SSE 频道让前端本地合成列表状态——前端需要为未打开会话维持订阅/状态机，复杂度大增；哑信号+refetch 复用既有链路，改动面最小。放弃。
