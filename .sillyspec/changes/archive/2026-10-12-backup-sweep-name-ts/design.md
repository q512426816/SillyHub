# 设计记录（Design Record）— 2026-10-12-backup-sweep-name-ts

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

aa809dc91 用 utimes(backup, now) 把备份保留期锚定创建时刻，但盖戳是 best-effort（`.catch(() => {})`，属主/文件系统 EPERM 即失败）；rename 又继承被备份残留的旧 mtime——两事件叠加（残留本来就老 + 盖戳失败）时，sweepStalePullScraps 按 mtimeMs 判 7 天会把刚创建的备份立即清掉，7 天人工取回窗口归零，而备份里可能有未回灌的本地改动。备份目录名本身内嵌创建时刻（`${base}.pre-junction-backup-${Date.now()}`，ff8eb4ce3 引入）——修法：清扫时解析名字尾部内嵌 ts，取 `max(mtimeMs, 内嵌 ts)` 计龄（解析失败/更小则回落 mtime），双信号均老才清。保守方向：任一信号新鲜都保留，绝不误删。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- 仅 `sweepStalePullScraps` 内部计龄逻辑（私有函数，签名不变）；可观察行为变化一处：备份目录在「mtime 老 + 名 ts 新」组合下不再被清扫（缺陷行为修正，无消费方依赖旧行为）。tmp/trash 10 分钟与备份 7 天保留期常数零变化。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   计龄基于创建时固化的目录名 ts 与文件系统 mtime，均不随读取时序漂移；并发 pull 各自产生独立命名的备份/残留（名含 Date.now()），清扫互不影响（既有语义）。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   清扫与新建备份并发时：新备份名 ts 新鲜 → 即使 mtime 尚未盖戳（utimes 在 rename 后异步落）也不被另一协程的清扫误删（本修复恰好收窄了该窗口）；rm 对不存在路径 force 静默，双清扫幂等。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   不适用：纯读-判-删，无状态迁移；解析失败回落 mtime 与旧行为一致，无新失败面。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   目录名前缀 `${base}`（=workspace specDir basename）隔离各 workspace 残留；内嵌 ts 只影响本前缀条目计龄，不跨 workspace。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：机器时钟回拨后创建的备份名 ts 大于「现在」，两信号均不老 → 备份保留至时钟追平——与 mtime 语义下时钟回拨的行为一致（既有同款边界），且方向是保守保留，可接受。
- 放弃方案 A：utimes 失败时改同步重试/换 fstat——盖戳失败的根因（属主/文件系统 EPERM）重试同样失败，fstat 取不到创建时刻（跨平台不可移植）；名字内嵌 ts 是创建时刻唯一可靠的跨平台载体。
- 放弃方案 B：清扫改为「7 天内以名 ts、之外以 mtime」的切换语义——比 max 更复杂且无额外收益；max 即「双确认才删」，语义最简最保守。
