# 决策记录（Decisions）— 2026-10-23-pre-session-draft-persist

## D-001@v1: 设计期风险与放弃方案（底稿）
- 类型：process
- 状态：confirmed
- 答案：- **本变更显式反转前序裁决**（须记 decisions 新版本取代）：`2026-10-23-session-input-clear-fix` FR-04「预会话恒空白、新建即弃稿」与 `2026-10-23-session-dialog-input-align` FR-04「idle 恒空白」。复潮条件已满足——用户实测后显式要求保留（本次 --input 原话）。两处被反转用例（「同一入口重进：输入框恒空白」「同 workspaceId 重开 dialog：恒空白」）就地改写为恢复语义，防口径漂移。 - 最大风险：清空后「组件卸载早于写 effect」丢清空事件 → 回来回显旧 AAA。评估：写 effect 在 input 变化的 commit 后同步 flush，用户「清空→切走」是人手两个操作，时间上必然晚于 effect 执行；唯一理论窗口是程序化清空（无）与清空后同 tick 卸载（无此路径）。风险可接受，FR-02 用例锁定。 - 放弃方案 A「预会话卸载钩子里补写草稿」：为不存在的窗口加防御，卸载钩子读 state 闭包易踩过期值（前序变更已知陷阱），不引入。 - 放弃方案 B「把预会话草稿并到每入口一个 sessionStorage」：用户明确要求刷新（新标签/重开浏览器）也保留，sessionStorage 不满足。 - 放弃方案 C「回读时同时回显 @ 联想/附件」：草稿键只存文本（R-7 语义），附件与 @ 绑定需重选是既有裁决，不扩scope。 - 明确边界（可接受）：同一入口的预会话草稿不区分「哪个用户意图」——只要没发送，重进就恢复；用户想丢弃就清空（FR-02 即为此设计）。 - 明确边界（可接受）：预会话草稿无 TTL（会话草稿同款），残留量级 = 入口数 × 一条文本。
