方案 A 4 处纯文本节点直接换成 MarkdownText 组件。 diff 最小，但表格横向滚动、字号对齐等卡片适配需要在 4 处分别手写——本原型演示的是「直换、未做适配」的自然效果：注意下方宽表格已溢出卡片边界（真实页面中卡片列更窄，溢出更明显）。认真补齐 4 处样式后效果可追平方案 B，但后续每改一处样式都要同步 4 个地方，易漏易漂移。
方案 B（推荐） 新建约 20 行的 CardMarkdown 薄壳组件（包 MarkdownText + 卡片场景适配），4 处统一调用。 正文正常渲染 md（标题 / 加粗 / 列表 / 行内代码 / 表格 / 代码块全部生效），宽表格在卡片内横向滚动（下方可滚动查看被截断的列），字号统一、行距对齐。适配集中一处，后续其它卡片场景（变更文件预览、会话附件卡）可复用，测试单点覆盖渲染 + 安全过滤。
方案 C 方案 B 的全部效果 + 卡片视觉重构。 卡片头加品牌色条与锚点链接图标、小节元信息条（作者 / 创建时间，来自 frontmatter）、表头品牌色卡片化。视觉最完整，但超出本次已确认的需求范围（你此前已确认只做渲染改造），验收面与回归风险更大，工期也更长。

SillySpec 文档驱动开发流程🔥
  • 执行顺序：文档 → 读现有代码 → 写测试 → 写实现 → 跑测试 → 验收
  • 禁止无文档改代码、禁止先写代码再补文档
  • 新功能/大改动走完整流程：sillyspec run brainstorm → plan → execute → verify
  • 小修复/小调整：sillyspec run quick
  • 修改代码前必须说明依据的文档路径；实现完成后对照文档验收
  • 提交被 hook 拦截时禁止跳过，必须解决问题再提交
子项目构建 / 测试 / lint 命令🔥

monorepo 根无统一命令，必须 cd 到对应子项目：

子项目技术栈testlint
backendFastAPI + uvcd backend && uv run pytestcd backend && uv run ruff check .
frontendNext.js + pnpmcd frontend && pnpm testcd frontend && pnpm lint
sillyhub-daemonNode + pnpm (ESM)cd sillyhub-daemon && pnpm testcd sillyhub-daemon && pnpm lint

frontend/daemon 构建用 pnpm build；backend（Python）无独立 build 步骤。

backend Python 工程约定（model.py 单数 / ruff 配置）
  • 文件名单数：SQLModel 数据模型文件名是 model.py（非 models.py），与 router.py / service.py 同级；找模型类 grep model.py 而非 models.py。
  • ruff 配置（backend/pyproject.toml）：line-length = 100
  • 提交前格式化：cd backend && uv run ruff format .
模块卡片 H1 用中文名（module-id）

平台（SillyHub）文档列表按 markdown 首个 H1 提取 title 展示（backend scan_docs parser._extract_title）。模块卡片 H1 必须写「# 中文短名（module-id）」全角括号格式（如 # 变更中心（change）），不能只写英文 module-id——否则平台文档列表显示一墙英文代号不可读。
