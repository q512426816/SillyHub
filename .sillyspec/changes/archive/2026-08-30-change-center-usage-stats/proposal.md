# 提案书（Proposal）

## 动机

变更中心管理着「变更」与「快速修复」两类工作，但用户看不到一件事**实际花了多久、烧了多少 token**：两个列表和详情均无时间三元组（开始/结束/耗时）与用量信息。数据面其实已齐备——执行记录层（`agent_runs` + `agent_run_model_usage`）有完整的时间、四维 token、调用次数、轮次，且变更侧有 `change_id` 派发锚点与会话绑定锚点、快速修复侧有会话绑定链路——只缺聚合出口与前端展示。

## 关键问题

1. **耗时不可见**：`changes` / `quicklog_entries` 表无 started_at/finished_at/duration 字段，用户评估一个变更的工作量只能靠翻会话和执行记录手工拼。
2. **token 消耗不可见**：会话维度上周已有用量统计（2026-08-29-session-usage-stats），但变更/快速修复是用户真正关心的工作单元——跨多个会话、多次派发的总消耗无从得知。
3. **无重复计数安全的聚合口径**：变更与会是多对多绑定，简单按会话整算会让共享会话的消耗在多个变更重复显示，需要明确的并集去重口径（D-002）。

## 变更范围

- 后端：新建 `change/usage_service.py` 聚合服务（去重执行集合 + 明细主源/四维兜底两段聚合 + 时间三元组 + 轮次）；两个只读端点 `GET /changes/{cid}/usage`、`GET /quicklog-entries/{ql_id}/usage`；`ChangeSummary` / `QuicklogEntryListItem` 各内嵌 `usage` 摘要计算字段（批量聚合零 N+1）。
- 前端：可复用用量卡组件（摘要行 + 分模型折叠明细 + 口径注脚）；变更列表与快速修复列表各加「执行」列；变更详情页与快速修复抽屉挂用量卡。
- 契约：`pnpm gen:types` 同步 `api-types.ts` + `backend/openapi.json`。

## 不在范围内（显式清单）

- 不做金额/计费折算（对齐运行时页/会话页先例）。
- 不做工作区级/全局汇总（运行时页 `/runtimes/usage` 已覆盖）。
- 不改 daemon 侧任何代码（用量已由既有 run 终态上报链路落库）。
- 零数据库迁移（不改任何表结构，全部 DTO 计算字段）。
- 不动移动端页面（`frontend/src/app/m/**` 后续单独迭代）。
- 不做实时逐 token 更新（数据粒度 = run 终态落库）。

## 成功标准（可验证）

- 变更中心两个 tab 列表各出现「执行」列；无关联执行显示「—」，其余显示耗时 + token 总量 + 次数。
- 变更详情页与快速修复抽屉出现用量卡：开始/结束/耗时/轮次/输入/输出/缓存读/缓存写/调用次数/命中率 + 分模型明细。
- 聚合数字与 DB 手工 SUM 一致（测试用例覆盖：并集去重、跨变更共享会话各计一次、兜底桶、时间三元组 NULL 组合）。
- 列表接口无 N+1（批量聚合单查询，既有 `test_enrich_projection` 回归通过）。
- 旧客户端/旧前端不读新字段不受影响（全部 optional 字段，零迁移）。
