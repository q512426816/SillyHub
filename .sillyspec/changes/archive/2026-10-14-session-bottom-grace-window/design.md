# 设计记录（Design Record）— 2026-10-14-session-bottom-grace-window

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

用户实测刷新落位随机（本机 19 轮复现 1 次），复现态特征完整锁定：scrollTop=602=布局早期瞬态假底、贴底判定 near 在加载期被某事件误清、RO 与 [turns] 贴底全死且无自愈路径。凶手路径低频竞态无法稳定复现定位（多轮写入审计在绿轮无异常）——放弃追凶，改加固式自愈：贴底记忆宽限窗（最近贴底 10s 内 + 无用户真实输入），期间任何内容变化/turns 提交强制钉底。不管谁误清 near，宽限窗内自动复活。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无接口/导出变化；TurnTimeline 内部新增宽限窗判据（两处贴底触发条件 OR 扩展 + 输入监听 effect + 时间戳 ref），对消费方透明。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

3. 切换/生命周期：refs 组件级随 key 重挂载归零（新会话重新受窗保护）；监听 effect cleanup 完整移除。
4. 作用域：window 输入监听为组件存活期，标记/时间戳组件内局部，无跨会话面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：非输入型让权路径（如浏览器自动滚动/读屏器）在窗内被拉回一次——真实用户四类输入覆盖 99% 场景，10s 窗口短且只在内容变化时动作。放弃方案：①继续追凶（19 轮 1 复现，取证成本失控，用户在等）；②near 被清后无限复活（用户真滚后内容更新会被反复拉回，破坏让权语义）。
