# 设计记录（Design Record）— 2026-10-16-archived-files-tab

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

归档变更也要能看到「文件与对账」（用户原话：归档留档区不显示 spec 文档）。做法最小化：
`change-tabs.tsx` 的 `visibleTabs` 改为恒返回四枚（`archived` 参数保留兼容签名、不参与判定）；
`page.tsx` 去掉 files 面板挂载上的 `!archived` 条件；信息栏对账入口归档态同在途一样指回
「文件与对账」。同步更新 4 个测试文件的对应断言。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

`visibleTabs(archived)` 签名不变（`archived` 参数保留），行为变化 = 恒返回四枚；
`ChangeOverviewSide` 无签名变化（仅归档分支的入口文案改回指「文件与对账」）；
后端端点/DTO/命令/文件格式：无。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   答：成立——`visibleTabs` 是纯函数（同入参恒同输出），不依赖到达顺序；tab 集判定与 URL 钳制互不依赖异步结果。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   答：多标签并发切 tab 为「后到者胜」（router.replace 各自覆盖 URL，不引入跨标签同步——上一变更 D-013 已声明同一取舍）；无共享可变状态。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   答：切换变更时 URL 残留的 `?tab=` 仍在可见集内（四 tab 恒定），不触发钳制也无不一致；面板数据由 react-query 按 workspaceId+changeId 键隔离，不串台。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   答：不会——本变更不新增取数，全部复用既有 queryKey（含 workspaceId 维度）；无跨仓/多实例面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：归档态恢复「文件与对账」后，范围对账卡在归档态显示降级信息（指路「产出 · 归档留档」）——与用户诉求（归档留档不展示 spec 文档全貌）不冲突：卡内有降级说明，文件树与预览照常可用。
- 试过放弃：仅对归档隐藏「范围对账」保留文件树——放弃：对账与文件树同属一卡拆开会造成半空卡，且用户诉求未要求拆。
- 死路：无（改动面小：visibleTabs 单函数 + page.tsx 挂载条件 + 信息栏入口文案）。
