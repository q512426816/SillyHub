# 设计记录（Design Record）— 2026-10-12-ws-ref-hover-tip-flip

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

用户反馈输入框标签的悬停路径浮层看不到。根因（浏览器实测定位）：会话输入框贴页面最底缘，标签悬停时鼠标 y 通常 >880，浮层定位在鼠标下方 16px（y+16）直接落到 940 高的视口之外（实测浮层 y=965）——DOM 存在但物理不可见，截图也拍不到。修复：浮层定位加「底部空间不足翻转到鼠标上方」逻辑（系统 tooltip 同款行为）——`y+16+TIP_EST_HEIGHT(48) > innerHeight` 时改为 `y-48-10`（顶部 clamp 8px）；同时 left 的视口 clamp 从 `-320` 对齐实际 max-width 改 `-336`。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `InputRefOverlay` hoverTip 渲染的 style.top 定位逻辑（下方 16px → 空间不足翻上方）；新增内部常量 TIP_EST_HEIGHT=48。props 签名零变化。
- 后端 0 端点 0 schema。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

   浮层位置随每次 pointermove 的坐标重算，无乱序累积；判定用当次渲染的 window.innerHeight。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

   纯渲染定位计算，无共享可变状态。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

   视口 resize 时已渲染浮层不主动重算——但任何一次鼠标移动即按新 innerHeight 重定位（悬停场景鼠标必在动），可接受；浮层随指针移出即卸载，无残留。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

   定位纯客户端视口几何，无数据面。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

风险：TIP_EST_HEIGHT=48 是粗估（实际两行文本≈42px）——翻转判定略保守（早翻），只影响翻转时机不影响可见性。放弃的方案：渲染后读实际高度再翻（useLayoutEffect 二段定位）——复杂度不值（估高误差只导致提前翻转，无功能影响）。
