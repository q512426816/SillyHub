1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？——不适用：打包为单会话串行动作，无事件时序面；「打包后-部署前」窗口内他人提交不改变已打镜像内容（校验锚在打包时点）。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？——两个会话并发打包：各自产出各自 images.tar.gz（本地文件互不干扰）；并发部署仍可能互覆（脚本闸门管打包源合规，不管部署时序）——剩余风险由 skill §0「部署后 commit_sha 核对」兜底发现。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？——安全：校验段只读 git 状态；脚本中断不产生副作用（校验在构建之前）。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？——本仓部署脚本只管本仓；worktree 内打包会命中「分支非 main」闸门（worktree 分支名 sillyspec/*）——正是事故场景被拦的机制。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：闸门挡不住「两个会话都从 main 打包、先后部署」的时序互覆（后部署者覆盖先部署者——若两者都是 main 且后者更旧则仍回退）。兜底：§0 的部署后 commit_sha 核对能立即发现；彻底解（部署互斥/登记表）留待需要更多实证后做。放弃的方案：a) 只改 skill 文档不加脚本闸——事故证明纯约定无效（并行会话各行其是），机械闸必须；b) 部署登记文件 .last-deploy 比对——需要 load-and-up.sh 也改+跨会话写同一文件，复杂度高于本次 thin 边界，列为后续。
