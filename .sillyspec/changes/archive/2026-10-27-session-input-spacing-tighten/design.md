# 设计记录（Design Record）— 2026-10-27-session-input-spacing-tighten

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

用户在浏览器开发者工具定位到会话页输入区链上 pt-3/pt-1/pb-4/py-2/pb-3/py-5 层层叠加致留白过大。改法：桌面与手机共用的 SessionPanelPage（消息滚动区 py-5→pt-5、输入区容器两处删 pt-3、区底两处删 pb-3）与 SessionInputBar（footer 删 pt-1+pb-4、输入框容器/textarea/@联想浮层镜像三处 py-2→pt-2）共 2 文件 9 处类名微调。选共用组件单点改：手机会话页经 SessionPanel variant="mobile" 复用同组件（排查确认无独立竖向间距分支），一改两端同步生效，无重复维护。依据：用户 DevTools 取证 + 确认清单（2026-10-27 会话问答）。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无接口变更（纯 className 字符串调整，组件 props/签名/事件零变化）。@联想浮层 overlay 的 overlayClassName 与 textarea className 同步 py-2→pt-2，保持浮层-正文垂直对齐契约（InputRefOverlay 镜像语义）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

1. 乱序/迟到到达：不适用——纯静态样式类名调整，无事件流/异步输入面。
2. 并发写：不适用——编辑时组件文件由本会话独占提交（显式 pathspec）；无共享可变状态。
3. 切换/生命周期：安全——类名调整不触碰组件状态机/会话生命周期；@联想浮层镜像同步改防止浮层错位（唯一交互耦合点已覆盖）。
4. 作用域：桌面与手机共用组件同步生效（有意行为）；dialog 模式命中的 py-2 属告警横幅（另一区域）不动；gap-3 不在输入区链上不动。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：@联想浮层与 textarea 垂直对齐漂移——已通过 overlayClassName 镜像同步改消除，并由 draft-scope 回归用例兜底。试过放弃：按用户片段字面把 py-2/py-5 上下全删——会让消息顶行贴边/输入框过扁，按用户片段「只有下内边距」的口径改为只去下保上（pt-5/pt-2），更贴近其真实意图（收紧消息区与输入区之间的空隙）。
