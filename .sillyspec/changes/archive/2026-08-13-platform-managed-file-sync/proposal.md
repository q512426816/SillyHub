# 平台管理 spec 文件增量同步 — 提案

## 动机

当前 spec 文件同步（daemon spec-sync）把整个 specDir 打成 tar **全量覆盖**服务器 spec_root——量大、无并发保护、无变化识别、删除不传播。用户明确要**平台管理文件**，且多用户/设备对应同一 workspace 是正常情况，需要增量推送 + 并发保护 + 软删除备份。

## 关键问题

1. **量太大**：每次全量整树，含 `.runtime/` 纯负担（worktrees 可达 GB）。
2. **无并发保护**：多写者各自推，后推整树覆盖前推，静默丢（进度同步有 base_ts 409，文件没有——不对称）。
3. **无变化识别**：文件没变也全量重传；路径变化（rename）靠整树+旧文件保留掩盖，增量后失守。
4. **删除无备份**：现状删除不传播；要支持同步删除但服务器不能真删，要留备份可找回。

## 变更范围

- **增量推送**：文件级，只推变化（add/update/delete/rename），SHA-256 判内容。
- **多写者乐观锁**：文件级版本号，base_version 过期 409 拒 + 人工拍板。
- **软删除备份**：删除移出 spec_root 到备份区（`<workspace 数据根>/spec-backups/`）不物理删，可找回。
- **rename 显式 op**：路径变化识别为 rename，旧 hash 相同不重传内容。
- **兼容**：旧 tar 端点保留（首同步/回退），旧客户端仍可用。

## 不在范围内（Non-Goals）

- 不做自动合并（只 409 拒绝 + 人工拍板）。
- 不做逐文件内容 diff 合并。
- 不做 `.runtime/` / `sillyspec.db` 增量同步。
- 不改 pull 侧（服务器→daemon 仍整树 tar）。
- 不做文件历史版本查询 UI（本次只做存储侧软删除备份）。

详见 `design.md` §3 非目标。
