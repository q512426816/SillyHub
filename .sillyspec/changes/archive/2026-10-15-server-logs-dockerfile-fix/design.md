# 设计记录（Design Record）— 2026-10-15-server-logs-dockerfile-fix

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

改两处：① backend/Dockerfile 构建期 mkdir 行加 /data/logs 并入 chown app:app（对齐 /data/spec-workspaces 既有惯例——容器内 app 用户运行，/data 属 root，运行期 mkdir 权限被拒是「日志文件尚未生成」的直接根因）；② backend/app/core/logging.py 的 configure_logging 降级分支向 stderr 打一条含「文件日志不可用」与异常原因的可见警告——原设计「静默降级」让权限缺陷在生产无从发现（页面只剩空态提示）。选 Dockerfile 预建而非改 compose volume：镜像自包含、不引入部署编排变更，与既有 /data 预建惯例同模式。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无函数签名/端点/文件格式变化。configure_logging 行为增强：目录不可建时新增一条 stderr 降级警告（新增输出，无输入输出签名变化）；Dockerfile 为构建指令（镜像内容新增 /data/logs 目录，对运行时 API 面零影响）。测试面新增 test_configure_degraded_prints_warning 用例。

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？——不适用：构建期目录预建与启动期警告均无事件时序面；日志写入顺序由既有 FileWriter 单点顺序写保证（2026-10-15-server-logs-panel 既有设计）。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？——预建目录发生在镜像构建期（单线程 Docker 层）；运行期多 worker 并发写同一日志文件属既有 2026-10-15-server-logs-panel R-02 已登记面（单 worker 部署，不新增）。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？——安全：目录预建幂等（mkdir -p），降级警告仅在启动时打一次，进程重启后重试；容器重建不丢行为（目录在镜像层）。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？——不串台：日志文件是宿主/容器级单实例资产（非工作区数据面）；多 backend 实例共享 volume 时按 R-02 既有口径（交错仅个别行）。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：已部署的服务器若以 bind-mount 覆盖 /data（宿主目录属 root），镜像内 chown 不生效——预建目录会被挂载遮蔽，仍可能权限被拒；此时降级警告（修复②）会在容器日志里明示原因，按日志处置（宿主侧 chown 或配 log_dir 指向可写路径）。放弃的方案：改 docker-compose 加 volume 挂载日志目录——引入部署编排变更且服务器侧需手工迁移，超出「镜像自包含」修复边界（如需持久化日志到宿主，后续独立变更处理）。
