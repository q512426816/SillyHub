# 设计记录（Design Record）— 2026-10-23-marquee-ticker-speed

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

用户反馈条目内部文本滚动太慢。只改 `frontend/src/app/globals.css` 中 `.sh-live-marquee-ticker` 的 `animation` 时长：`8s → 3s`。双份文本结构、`translateX(-50%)` 循环方式、轨道 rAF 推进、耗时/转圈逻辑均不动。原 8s 一份按常见 300px 摘要约 37px/s，3s 约 100px/s，流动感明显增强且仍可辨认片段。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `globals.css` `.sh-live-marquee-ticker` 的 animation-duration `8s → 3s`；类名、keyframes 名、DOM 结构不变。
- 组件 props、导出函数、后端 API / daemon 协议：**无变化**。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   - 成立。仅 CSS 动画时长，与事件顺序无关。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   - 无写面；样式静态。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   - 安全。reduced-motion 覆盖规则保持 `animation: none`；组件卸载无计时器。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   - 不涉及数据。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：速度过快时短文本重复感更明显；3s 为折中值，若仍不合适继续微调该单一常量即可。
- 放弃方案：按文本长度动态计算时长（需要测量宽度、增加 JS 复杂度，收益有限）；改轨道整体速度（用户只反馈条目内部滚动慢，轨道行为已被确认）。
