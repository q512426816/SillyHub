# 决策记录（Decisions）— 2026-10-13-subagent-stub-reconcile

## D-001@v1: 风险与死路（design 槽4 收割）
- 类型：process
- 状态：confirmed
- 答案：最大风险：对账把「真在跑」的 stub 误标终态——数据源是服务端权威行（清扫只会标 stopped 不会标 completed），误标面收敛为「快照行本身错误」，与任务清单页签同源同信，可接受。次风险：TurnRow memo 对新 prop 的比较——Map 以 useMemo 稳定引用，仅快照变化时重建，不破坏流式期间的 memo 收益。 试过但放弃的方案：① 装配器给 stub 补元数据槽并路由 [TASK_*] 行——窗口外行根本不在装配输入里，治不了根因，且动 stub 类型契约波及面大；② 时间线按 run 全量补拉日志（窗口截断的根治）——改分页架构，性能取舍（ql-20260916-013 有意为之）推翻成本高，收益仅此一处展示，不做；③ stub 徽章改中性文案「已结束(见任务清单)」——不解决名字问题且是降级不是修复；④ 后端给快照行补「是否关联时间线」之类新端点——现有 tool_use_id 关联键已够，零后端改动是本方案的显式优点。
