## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

在 deploy/docker-compose.yml 的 litellm 服务块尾（mem_limit 之后）新增 logging 块：`driver: json-file` + `max-size: "10m"` + `max-file: "3"`。这是 2026-10-05-litellm-crashloop-quarantine 的结构性加固补全——profiles 门拦住默认 `up -d` 路径，但注释里写明的复验路径（`--profile litellm` 或显式点名拉起）一旦执行，坏构建镜像在 restart:always 下仍会 crash-loop，而整个 deploy/ 无任何日志轮转配置，json-file 默认无上限，低配服务器磁盘会被打满。

选服务级 compose 配置而非其它方案的依据：改宿主 /etc/docker/daemon.json 全局默认——要动服务器系统状态且影响所有容器，超出本仓变更面；给全部服务统一加 logging——核心服务的日志保留策略变化未评估（排障时可能反而需要更长的日志留存），行为面扩大，留待专门变更评估。只给已知会 crash-loop 的 litellm 加有界轮转，变更面最小且与既有隔离门互补。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无函数/端点/命令/文件格式变化。对外可见行为仅一条：litellm 容器日志由 Docker json-file 驱动有界轮转（单文件 ≤10m、保留 ≤3 份、总量 ≤30m）。默认启用集合、镜像、网络、端口、卷、健康检查、restart 策略均不变。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   不适用——纯静态声明式编排配置（YAML），无事件流与时序假设。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   日志文件由 Docker 守护进程单方管理（容器 stdout 重定向），轮转由 json-file 驱动原子执行，无双写方冲突；YAML 本身是仓库内单一文本文件，git 并发按常规文本冲突处理。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全——logging 选项在容器创建时生效，容器删除重建后轮转计数重置，无跨生命周期残留状态；回滚=还原 YAML 后 recreate 容器即恢复无界行为。服务仍被 litellm profile 门控，默认栈容器完全不受影响（不 recreate）。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会——logging 配置仅作用于本 compose 项目内 litellm 一个服务，不触碰宿主全局日志配置，也不影响同文件其它服务；本机与阿里云服务器共用同一文件同一语义。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：轮转上限过小导致 crash-loop 排障时关键 traceback 被截丢——取 10m×3=30m 兼顾低配磁盘与排障留存（该服务已设 PYTHONUNBUFFERED=1，崩溃 traceback 即时 flush，单份 10m 足够装下完整崩溃记录）。试过但放弃的方案：①宿主 daemon.json 全局默认轮转——动服务器系统状态、影响所有容器，超出本仓变更面；②全服务统一 logging——核心服务日志保留策略变化未评估，扩大行为面，留待专门变更。
