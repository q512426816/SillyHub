# 设计记录（Design Record）— 2026-10-22-protect-cjk-source

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

生产复现确认：`opus-mt-en-zh` 的源端只有英文词表，遇到中文 token 时 tokenizer 产出 `<unk>`，束搜索随后陷入重复输出——`"合并键应该是工区不是厂房"` 被译成 `“\ ”`，`--title "单位级明细表合并键=工区（用户实测反馈）"` 变成一串反斜杠。根因在源端，调译后处理或段级跳过都治不了（中文引用与英文在同一自然段，段级判定按占比会整段放行）。

修复：在 `chunking._PROTECT_RE` 增加最高优先级的「中文片段」分支（汉字 + 中文/全角标点连续段），与围栏代码、行内代码、URL 同等待遇——不送翻、原样保留。送进模型的源文本因此不再含中文 token，解码崩溃消失；中文引用逐字保留，英文正文照常翻译。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- 无公开签名变化；`split_protected` 的切分结果多出「中文保护段」一类（`SourceSegment(translatable=False)`），拼接保真不变。
- HTTP 端点与响应结构不变。
- 既有 `should_translate_segment` 段级判定保留（纯符号/空白段兜底），行为不变。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立：保护切分是纯函数、与顺序无关；重组仍按段序拼接。段索引变化由 `split_paragraph_segments` 统一处理，回填逻辑不变。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

无共享写面：切分结果均为请求内局部对象。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全：纯函数无生命周期状态；引擎 fail-soft 路径不变。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会：无全局状态新增；缓存键仍按块文本哈希，切分变化只影响新块内容。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：中文片段保护后，正文段可能被切碎（引号、空格、英文单词片段），块数上升、单块过短；模型对极短片段（如孤立的 `"` 引号）可能产出空串或原样。可接受——碎片不携带语义，且 `should_translate_segment` 对无字母/汉字段直接跳过。
- 风险：中英紧邻无空格（如「这个是chunk」）会出现中文保护段与英文正文段相邻，重组顺序仍保真；可接受。
- 风险：轻量模型对英文长句的翻译质量本身一般（本次复现中 `sillyspec decisions add` 被译成「愚蠢的决定添加」），属模型能力上限，不在本变更范围；如需质量提升应另行更换更大模型。
- 放弃方案：调高段级判定的中文占比阈值。放弃理由：中文引用只占句内小部分，占比阈值永远够不到，整段仍送翻。
- 放弃方案：译后清洗反斜杠。放弃理由：治标——中文引用已经被破坏，清洗无法恢复原文语义。
