## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

参考 lemomo-ai/lemo-opuscar 的「纯代码拍片」思路：不用视频模型、不用视频文件，宣传片就是一页代码——单文件 HTML 内用 Canvas 2D 按主时钟逐帧实时渲染一部约 98 秒、8 幕的电影，配乐用 WebAudio 振荡器实时合成。放在 `docs/promo/` 下，与仓库现有 docs 静态产物（原型 HTML、PPT 等）同列，不触碰 frontend/backend/daemon 任何平台代码，零部署成本、双击即开。

影片结构（时间轴为确定性函数，seek 严格可重放）：序幕「失控的代码」（终端+红色告警，制造张力）→ 标题揭示（粒子汇聚成 SillyHub）→ 规范驱动（SillySpec 五阶段流水线+门禁）→ 架构（README 架构图动画化：浏览器→backend→存储；daemon→Agent）→ 多 Agent 编排（12 宿主星座+并行 worktree 车道）→ 实时可视（SSE 日志流+拓扑+看板）→ 团队与安全（RBAC 盾+双层审批门）→ 尾声 CTA（数据收束成 logo，`make up` 一键起）。所有文案以 README 为唯一事实源。视觉用 AI-Native 品牌紫 #7C3AED 主导、青 #0891B2 点缀，深色电影底+胶片颗粒+遮幅黑边，与平台主题血缘一致。

播放器为 DOM chrome（海报页/播放暂停/章节进度条/静音/重播/快捷键），画布只负责画面；音乐按「小节和弦轨道表」调度，与画面共用同一主时钟，seek 时两者同步重启对齐。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无平台接口变化：不改 backend 端点、前端路由、daemon 协议、构建产物。新增的对外可见面只有两个静态文件（docs/promo/sillyhub-promo.html 播放页、docs/promo/README.md 说明），无导入关系、无构建依赖。页面内部约定：`#film` 画布元素 + `window.__promoFilm` 调试句柄（play/pause/seek/t0..t1 时间轴只读），仅用于浏览器验证，不承诺任何跨页契约。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   成立。影片画面是主时钟 T 的纯函数（粒子位置由种子化伪随机+局部时间解析计算，非积分状态），事件只有用户输入（播放/暂停/seek），无网络与消息到达顺序问题；seek 乱序跳转任意次，画面与配乐都由 T 决定，无乱序损坏面。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   不适用：纯静态单文件页面，无后端、无存储、无共享可变文件；单浏览器标签页内单 rAF 循环串行绘制，WebAudio 调度器与绘制循环同线程，无并发写。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   安全。标签页隐藏时自动暂停（visibilitychange）；AudioContext 仅在用户点击播放后创建、静音只动 master gain 不销毁节点；重播=时钟归零重放；页面刷新无任何持久状态需要清理。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   不会。无外部数据源、无 localStorage 写入、无网络请求；多开标签页各自独立渲染，互不共享任何状态。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：Canvas 中文排版与不同操作系统字体栈差异导致观感不一致——用系统中文栈（PingFang SC/微软雅黑/Noto Sans SC）+ 关键标题走 canvas measureText 动态布局兜底，避免外链字体（保 FR-01 零依赖）。
次要风险：低端机粒子量过大掉帧——粒子数与屏幕像素解耦（按 1920×1080 逻辑坐标设计，数量固定上限），主循环只做一次 clear+draw，无离屏抖动。
放弃的方案：①嵌入真实视频文件（webm）——违背「纯代码拍片」参考思路且体积失控，弃；②用 Three.js/WebGL 做三维粒子——CDN 依赖违背 FR-01，手写 WebGL 工程量与收益不成比，2D Canvas 已够表达本片视觉，弃；③接平台前端做 Next.js 页面——宣传物料应独立分发（发别人看/挂静态托管），绑进应用反而要求起服务，弃。
