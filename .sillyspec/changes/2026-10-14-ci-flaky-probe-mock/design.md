# 设计记录（Design Record）— 2026-10-14-ci-flaky-probe-mock

## 做法概述

frontend-ci 在 d850b45fe 仍红：`session-history-scroll.test.tsx`「连续 before 翻页到头」`expected 3 to be 2`。本地插桩实证：0bd70bc47（2026-10-13-load-earlier-full-turn）给满页翻页新增 limit=1 页顶探查（轮边界对齐）后，该用例真实 API 序列 = 翻页(400) → 探查(1) → 翻页(400)，共 3 次 before 调用；探查 push 使计数在微任务级窗口内短暂为 3，而断言 `waitFor(toBe(2))` 依赖「探查 push 后、翻页#2 push 前」的瞬态窗口命中 2——本地快机碰巧命中，CI 慢机必挂。属测试 mock 未适配探查请求形态（同文件 105 行先例已适配：空响应不进游标记账），非生产缺陷。

修法：FR-03 用例 mock 照抄 105 行先例——`if (opts?.before && opts.limit === 1) return [];`（探查空响应、不 push），opts 类型补 `limit?: number`。修后计数只含翻页本体，单调升至 2 后恒定，断言命中终态。

## 接口契约

生产接口/端点/命令/文件格式：无变化。

测试内部：`getAgentSessionLogs` mock 的 opts 参数类型由 `{ before?: string }` 扩为 `{ before?: string; limit?: number }`（同文件 102 行先例同款签名）；探查分支返回 `[]`（页顶轮完整语义，与 105 行先例一致），翻页分支行为不变。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：本病灶即「断言依赖瞬态窗口」的时序缺陷——修后计数单调（探查不回填），waitFor 命中恒定终态，检查时机不再影响结果。
2. 并发写：mock 单线程微任务序执行，probe 分支前置判断（limit===1）在 push 之前完成，无并发面。
3. 切换/生命周期：该用例单会话单循环到头即止（到头后 hasEarlier=false、入口消失断言不变）；探查空响应语义「页顶轮完整」与先例用例一致，不触发直达整轮降级链。
4. 作用域：仅此测试文件内 mock 行为，组件与其它测试文件零触碰。

## 风险与死路

最大风险：探查返回空响应被组件判「页顶切轮」走直达整轮链路引入新调用。核对 0bd70bc47 语义：空响应 = 紧邻更早行不存在/同轮完整，不触发直达；同文件 105 行先例用例（3 次触顶翻页）已在此口径下稳定运行，本修复复用同一口径。

试过但放弃的方案：
- 放宽断言为 `toBeLessThanOrEqual(3)`——否决：把竞速瞬态合法化，计数契约失真（翻页本体就是 2）。
- 修组件把探查与翻页在 tick 间去重——否决：探查是 0bd70bc47 有意设计且组件行为正确，生产代码零改动约束下不应动。
- 改用固定 waitFor 终态信号（入口消失）替代计数断言——部分吸收：保留原有后续断言（入口消失、scrollTop=0）不动，仅修计数口径，最小侵入。
