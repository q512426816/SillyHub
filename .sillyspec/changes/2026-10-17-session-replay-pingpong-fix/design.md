# 设计记录（Design Record）— 2026-10-17-session-replay-pingpong-fix

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

改 `frontend/src/stores/session.ts` 的跨标签 storage 回放监听器：回放前先与本地当前状态逐字段比对——accessToken/refreshToken 字符串直比，user 用键序无关稳定键（键排序后序列化）比较——只对真实差异字段 setState，全等时静默返回（不 setState 即不产生 persist 写盘）。

选此方案依据：乒乓环路的自持能量来自「回放→persist 写盘→对方 storage 事件→回放」，从回放侧掐掉同值写盘即让环路失去自持条件（生产实证 2026-10-17：两标签各持不同过期 token，/api/auth/me 每秒 10 条 401 刷屏 11 小时）；同时不改 persist 配置、不动任何调用方，真实跨标签同步语义完整保留，改动面最小。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

无对外签名/导出变化：`useSession`、`SESSION_STORAGE_KEY`、类型导出全部不变。模块内部新增私有函数 `sessionUserKey` / `isSameUser`；对外可见的行为变化仅一处——storage 事件回放从「无条件 setState（必写盘）」变为「差异回放：全等静默、部分差异只回放差异字段」。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

1. 乱序/迟到到达：成立。比对基准是「收到事件那一刻的本地状态」，回放总是向远端最新值收敛；迟到的同值事件被静默，不会把已收敛状态回退。
2. 并发写：与原行为一致。A 续票与 B 换账号并发时后到事件覆盖先到（值不同必回放），差异比对不引入新丢失面；同值事件静默只是省掉一次等值写盘。
3. 切换/生命周期：安全。静默路径零状态迁移；patch 仅含 accessToken/refreshToken/user 三字段，与原行为一样不触碰 hydrated 生命周期标记。
4. 作用域：无新增串台面。比对只针对本 key（SESSION_STORAGE_KEY）信封内字段，localStorage 同源共享语义与原行为一致。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

最大风险：比较漏判让乒乓换个字段复活。user 若未来从扁平对象演化为嵌套可变对象，现行「键排序后序列化」只对顶层键排序、不递归——需升级为递归 canonical（或改存单调版本号比对），session.test.ts 的键序用例会先红提示。

放弃的方案：①自定义 storage 包装层做写前去重——改动所有落盘路径，风险大于收益；②比较完整信封原始字符串——两端内存 user 对象键序不同会令字符串恒不等，乒乓换字段复活；③给 (dashboard)/layout 的 fetchMe 加节流——只治标，每秒 10+ 次 setItem 的写盘风暴仍在。
