# 设计记录（Design Record）— 2026-10-23-marquee-queue-window

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

把跑马灯的渲染队列从「最多 200 条」收敛为「固定最近 12 条」：`LIVE_MARQUEE_MAX_ENTRIES` 由 200 改为 12，
`deriveLiveMarqueeEntries` 继续截断最旧、只返回最新 12 条。组件轨道渲染条目数因此恒定 ≤12，
轨道总宽约 `12 × (256px + 20px)` ≈ 3.3k px（此前 200 条约 5.5 万 px），DOM 与高频重渲染成本大幅降低。

窗口滑动逻辑继续复用现有 `resolveMarqueeTarget` / offset 补偿：
窗口满后每次新增事件 → 首条 id 变化 → 目标回到 base、offset 先右移一条再平滑滚回，视觉连续；
窗口未满时内容增长仍只向最新推进。首挂载仍直接定位最新，不循环。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `LIVE_MARQUEE_MAX_ENTRIES` 常量值 `200 → 12`（导出名不变）。
- `deriveLiveMarqueeEntries` 签名不变，返回长度上限变为 12。
- 组件 props / 其余导出 / CSS / 后端接口：**无变化**。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   - 成立。截断按段文档序保留最后 12 条；迟到段追加为最新一条，旧内容按队列丢弃。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   - 无写面；仅组件内状态。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   - 安全。窗口滑动分支已有 offset 补偿与 rAF 停排/清理；内容未满 12 条时不触发滑动。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   - 不涉及数据；每个组件实例独立。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：窗口只有 12 条，用户无法在跑马灯回看更早事件。缓解：跑马灯定位是「感知」，完整过程在「进度」视图；12 条约 3 屏，滚动节奏足够。
- 窗口频繁滑动（每次新事件）：每次只前进一条且补偿平滑，视觉与性能均可接受；轨道总宽恒定，不累积。
- 放弃方案：① 保留 200 条（用户指出成本不必要）；② 只保留 10 条（12 条保留约 3 屏上下文，性能差异可忽略）；③ 用虚拟列表（12 条不需要）。
