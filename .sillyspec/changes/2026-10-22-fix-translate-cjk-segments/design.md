# 设计记录（Design Record）— 2026-10-22-fix-translate-cjk-segments

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

根因：`is_translation_worthy` 只在整条 item 上判定一次；中文正文夹英文代码块时，代码里的拉丁字符把整条的拉丁占比拉过阈值，整条通过后 `split_protected` 只保护代码/URL，剩余中文正文段仍以 `translatable=True` 送进 en→zh 模型，产出垃圾译文并置 `translated=true`（生产实测：`命令：`→`发件人:`，整段中文消失）。

修复：在 `chunking.py` 新增段级判定 `should_translate_segment`（只判语言占比：有汉字或拉丁字母且中文占比 <0.6 才送翻；纯符号/数字段不送），`service.py` 的送翻循环在切块前逐段调用，中文段保留原文；同时用 `translated_ids` 集合记录实际送翻（或缓存回填）过的条目，替换原 `_has_translation` 的粗粒度判定。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `app.modules.translate.chunking.should_translate_segment(text: str) -> bool` 新增（纯函数，段级语言判定）。
- `service.translate_items` 响应字段结构不变；`translated` 语义收紧为「实际送翻过」。
- HTTP 端点 `POST /api/translate/thinking` 契约不变（无 DTO 改动，无需 gen:types）。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？

成立：段级判定是纯函数、无状态，与段顺序无关；重组仍按 `chunk_owners` 顺序回填。既有乱序风险（旧读线程迟到响应）由请求 id 校验兜底，本变更不触碰。

2. 并发写：两个执行体同时操作同一数据/文件会发生什么？

无新增共享写面：`translated_ids` 是单次请求内的局部集合；进程内 LRU 仍走既有锁。

3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？

安全：判定与标记均为请求内局部状态，请求结束即释放；引擎 fail-soft 路径不变。

4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？

不会：无全局可变状态新增；缓存键仍含目标语言与文本哈希。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：段级只按语言占比判定，中英混排在同一段内（如「这个方法用 `cache` 缓存」）仍会整段送翻，模型对段内少量中文可能仍有破坏——整段送翻是现有粒度的边界，彻底解决需句级切分（成本高、破坏块保真）；当前修复覆盖生产实测的「中文正文 + 代码块」形态。
- 风险：纯数字/符号段判定为不送翻，若模型本可处理（无意义）不影响；可接受。
- 放弃方案：直接调高整条 worthy 阈值。放弃理由：会让「英文正文夹中文」也整条跳过，损失正常翻译。
- 放弃方案：前端也做段级判定。放弃理由：后端是权威兜底，前端重复实现易漂移；整条通过时请求成本可接受。
