# 设计记录（Design Record）— 2026-10-23-marquee-awaiting-indicator

## 做法概述

本变更怎么解决问题？改哪里、为什么选这个方案（一两段）。

LLM 生成间隙（工具已完成、下一段未到）没有日志事件，装配器无法派生该状态；但组件被消费方门控为
「仅运行中轮次渲染」，因此「最新真实条目非 running」即可判定处于等待态。在 `TurnLiveMarquee` 渲染层
追加一个合成条目 `marquee-awaiting`（icon `awaiting` → lucide `Sparkles`，status running）：
文本「等待模型响应 · 耗时」，耗时由组件从进入等待态起以 1s interval 更新（复用 `formatMarqueeDuration`）。
该条目只拼接进轨道渲染列表，不进入 `entries`、计时 Map、窗口滑动检测——新事件到达/回到 running 即消失并清零计时。

## 接口契约

动了哪些函数/端点/命令/文件格式？对外可见的签名或行为变化是什么（含「无」的说明）？

- `LiveMarqueeIcon` 新增枚举值 `"awaiting"`（渲染映射 `Sparkles`）。
- 组件内部新增等待态推导（latest.status !== "running"）与 1s interval 计时；无新增 props。
- `deriveLiveMarqueeEntries` / 其余导出 / CSS / 后端接口：**无变化**。

## 边界与并发（盲维四问——每问必答，答不了即设计缺口）

1. 乱序/迟到到达：输入或事件乱序时，本设计的假设还成立吗？
   - 成立。等待判定只看当前最新条目状态；新事件到达（无论顺序）只要使 latest 变 running 即消失。
2. 并发写：两个执行体同时操作同一数据/文件会发生什么？
   - 无写面；等待计时为组件内存。
3. 切换/生命周期：会话、请求或变更中途切换/中断时状态是否安全？
   - 安全。interval 在 effect cleanup 清除；轮终态组件卸载，等待条目随之消失；等待计时跨轮重置（组件重挂载）。
4. 作用域：跨工作区/跨仓/多实例时数据会不会串台？
   - 不涉及数据；每实例独立。

## 风险与死路

本方案最大的风险是什么？试过但放弃的方案及放弃理由？

- 风险：1s interval 在等待期间每秒触发一次组件重渲染；列表仅 12+1 条，成本可忽略，且只在等待态运行。
- 等待条目出现/消失使轨道宽度变化一条，target 单调规则下推进连续，短暂右端空档可接受（与真实事件到达通常几乎同时）。
- 放弃方案：① 从后端/daemon 发心跳事件（跨服务改动，收益不成比例）；② 用状态条文案兜底（已有「当前活动」但不持续、也无法区分等待与执行）；③ 等待条目参与 entries 队列（会污染窗口滑动与去重语义）。
