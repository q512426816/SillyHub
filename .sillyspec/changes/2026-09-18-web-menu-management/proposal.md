# 提案书（Proposal）

## 动机

菜单与权限体系为「代码定义 + 数据库分配」混合制，但运营侧缺口真实存在：4 个菜单（技能管理 / MCP 资产库 / 智能体档案 / 智能体会话）因无挂载权限对所有登录用户常显、无法按角色关闭；菜单显示名 / 排序 / 全局隐藏只能改代码发版；管理员调整时看不到「菜单→权限→角色」影响面。用户（2026-09-18）明确要求：按角色开关菜单显隐 + 菜单名/排序在线可调 + 菜单下挂权限只读可见。

## 关键问题

1. **4 个常显菜单无法按角色关闭**：`menu-permissions.ts` 中该 4 条 `permissions: []`，`hasAnyPermission` 对空列表返回 true（permission.ts:41），角色管理页无从收回——按角色维度存在盲区。
2. **菜单展示配置无运行时通道**：改名/排序/隐藏均为前端代码常量，任何调整都要走发版；管理页缺失导致「菜单」这一运营对象没有管理界面。
3. **影响面不可见**：角色管理页的权限勾选器只见权限名，不见「该权限控制哪个菜单、该菜单当前谁能看」，管理员需人肉对查两张表。

## 变更范围

- 后端：`Permission` 枚举 +5（`skill:read` / `mcp:read` / `agent_profile:read` / `agent_session:read` / `menu:admin`）+ group 前缀映射；新表 `menu_overrides`（menu_key 唯一 + label_override / sort_order / hidden）+ 迁移种子（4 新 key 授全部现存角色保现状）；子路由 `menu_overrides_router.py` 三端点（GET 认证、PUT/DELETE menu:admin + 审计）；`main.py` 挂载。
- 前端：`menu-permissions.ts` 4 菜单补 permissions + 新增「菜单管理」菜单项 + key 类型收紧为 api-types 生成的 Permission 联合类型；新 `lib/menu-overrides.ts`（拉取 hook + `mergeMenus` 纯函数）；`app-shell` 渲染经覆盖合并（menus 自身豁免隐藏防自锁）；新页面 `/admin/menus`（分组表格：改名/组内排序/全局隐藏/权限+持有角色只读展开，行级即时保存）。
- 测试：后端端点/门控/审计/种子；前端 merge 纯函数/页面交互。

## 不在范围内（显式清单）

- 不做在线新增/删除菜单条目（菜单=页面=代码交付物，随版本发布）
- 不做按角色改名/排序（D-002：覆盖全局生效；按角色维度只有显隐，由既有权限体系承担）
- 不做权限目录在线增删、接口鉴权点在线调整
- 不做路由级访问控制变化（URL 直达仍可行）
- 不纳管移动端 `m/` 导航（mobile-app-shell 不消费菜单注册表）
- 不做主题/图标在线调整

## 成功标准（可验证）

- 迁移后未做任何覆盖配置时，导航渲染与现状逐项一致（持任意角色的存量用户 4 菜单可见性不变；零角色用户例外见 R-07）
- 角色管理页可收回/授予 4 个新权限 key，对应菜单随登录用户权限显隐
- 管理员在 `/admin/menus` 改名/组内排序/全局隐藏并保存后，任意用户（含平台管理员）下次导航渲染即生效，全程无发版
- 每个菜单可展开查看挂载权限 key、中文名与持有角色（只读）
- 前端引用后端枚举不存在的权限 key 时 `tsc` 编译报错（FR-04）
- 无 `menu:admin` 权限调用 PUT/DELETE 返回 403；未认证调用 GET 返回 401
