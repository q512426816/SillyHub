# verify 增量重跑账本把「运行器基建失败」按测试失败计入失败批 → 失败批随轮膨胀

> 记录时间：2026-10-15 · 来源变更：2026-10-15-dsh-engine-acp（verify 阶段多轮实测）
> 状态：活跃坑（与 verify-jsx-batch-cmd-too-long.md 同源触发面；分块补丁在场后本记录仍建议保留
> ——账本语义未修，「基建失败重入」对任意基建类失败（argv 超限/runner 启动失败/批命令构造失败）
> 都成立）

## 现象

同一变更 verify 连续两轮，`⚡ 增量重跑面` 文件数单调递增：

- 轮1：增量重跑面 141 文件（前轮失败批 140 ∪ 基线以来变更 31）；
- 轮2：增量重跑面 159 文件（前轮失败批 155 ∪ 基线以来变更 73）。

触发面：jsx 批因 Windows argv 超限（`命令行太长。`，**非测试断言失败**）整批记为 failed →
进入「前轮失败批」增量账本 → 下一轮重跑面 = 失败批 ∪ 新增变更 → 批更大 → 更必然超限 →
膨胀循环；每轮还白烧后端 py 批（实测 2~9 分钟）。RERUN 失败签名（代码指纹 × 测试面 ×
环境探针）因测试面每轮不等而恒变——既不拦也失去去重意义；环境探针对「spawn 层 argv 超限」
不感知，修复落地前后签名无法据此放行。

## 根因

- 增量账本对批 failed 的判定**不区分「测试真败」与「运行器基建失败」**——后者无论重跑几次
  都不可能转绿，但每轮仍全额重入失败批并叠加新变更，账本只增不减；
- RERUN 失败签名没有「基建失败类」的独立维度（环境探针不含 argv 长度 / runner 可用性）。

## 复现

1. Windows 上构造一次 jsx 批 argv 超限（文件数 > 上限且未走分块补丁，或人为加长批前缀）；
2. 连续 `sillyspec run verify --done` 两轮以上；
3. 观察每轮 `⚡ 增量重跑面 N 文件（前轮失败批 M ∪ 基线以来变更 K）` 中 M、N 递增，
   且失败 reason 恒为「命令行太长。」（输出无任何测试级失败行）——账本把基建失败当测试失败。

## 建议修法

1. **批失败分类**：批 runner 非零退出但输出**无任何测试级失败行**（无 `×`/`FAILED`/
   `AssertionError` 等），或 reason 命中基建关键词（argv 超限/`E2BIG`/spawn 失败）→ 标
   `infra-failure`；`infra-failure` **不进「前轮失败批」增量账本**（或进独立 infra-retry
   集合、仅原批重跑一次即止）；
2. 增量账本对失败批设**上界**（如不超基线子集大小），膨胀判定成立时打印警示并降为全子集一轮重算；
3. RERUN 签名纳入「批构造指纹」（分块结果/命令长度/runner 版本），使分块补丁之类修复落地后
   签名自动失配、下一轮重跑一次收敛；
4. 逃生口文档化（本次实际使用）：`local.yaml test_strategy: full` 可切 `commands.test`
   （无 argv 文件清单，绕开 argv 上限与账本膨胀）单轮收口——用完记得还原 `module`。
