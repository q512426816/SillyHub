# 坑9：变更 DB 行被外部清除后平台永挂幽灵变更——sync 假成功 + 墓碑链失源

> 发现于 2026-10-13（事故变更 2026-10-13-new-change-e5a27813，本仓 multi-agent-platform）。
> 状态：已修复（sillyspec 仓变更 2026-10-13-sync-ledger-tombstone，归档于该仓 .sillyspec/changes/archive/；本仓 daemon/backend 无需改动）。

## 现象

平台变更中心出现一个名为 `2026-10-13-new-change-e5a27813` 的"进行中/头脑风暴"变更，永不消失；本地 `.sillyspec/changes/` 无此目录、本地进度库无此行、git 历史无痕。daemon 日志显示 22:57 reconcile 还对它跑过一次 `platform sync --change`（code 0，看似成功）。

## 根因（三段叠加）

1. **变更行被外部手段物理清除**（16:25:43，创建后 10 秒）：目录+DB 行全没了。sillyspec 官方删除路径（change-delete/unregisterChange）都保留 DB 行（status='deleted'/'archived'），物理删行只可能来自裸 SQL/rm——当日 16:29 有个调试会话就叫 "no-such-change"，基本是调试副产品。
2. **X1 墙碑链失源**：`sync.js _pushTombstone` 依赖 `serializeForSync` 读 DB 行，行没了返回 null 直接放弃（"方案 A 兜底"）——而平台侧镜像收敛对 changes 表行并不生效，只有 7 天占位行保护窗 + 全量 reparse 的慢兜底。
3. **CLI 假成功掩盖**：`sillyspec platform sync --change X` 对"变更无进度数据"只 warn，命令退出码恒 0（index.js 忽略 sync() 返回值）——daemon RPC（sillyspec.sync_change，2026-10-13 新上的 change-files-refresh 链路）按退出码回执 ok:true，假成功把"行缺失"彻底盖住。

## 修复（sillyspec 仓 2026-10-13-sync-ledger-tombstone）

- **删除台账** `src/deleted-ledger.js`：deleteChange（deleted）/unregisterChange（archived）事务提交后向 `.sillyspec/.runtime/deleted-changes.jsonl` 追加 `{name,status,at}`（追加-only、fail-open、latest-wins、坏行容错）——终态凭证脱离 DB 行存活。
- **台账墓碑**：`sync()` 行缺失分支查台账，命中终态即合成最小载荷（changes[0] 携台账 status + current_stage='archive'）POST 既有 progress 端点；平台 `_apply_cli_tombstone` 据此收敛 location（base_ts 缺失按平台契约"无条件接受"，无 409 面）。quick-* 豁免；never-existed（打错字）不发墓碑防误删真变更。
- **假成功修复**：`platform sync --change` 失败（errors 非空）exit 1 + stderr 明确错误——daemon RPC 如实上报失败。
- 测试锚：sillyspec 仓 test/deleted-ledger.test.mjs（7 例：落账/fail-open/墓碑补推/退出码/容错/豁免），独立评审 PASS。

## 现场清理（2026-10-13 已执行）

平台 Postgres `changes` 表该行经引用核查（9 张 FK 表全零引用）后物理 DELETE；本地 `.sillyspec/.runtime/` 残留的 prompt-inject/watcher 孤儿文件无害保留。

## 验证要点

- `sillyspec platform sync --change <不存在且无台账>` → exit 1（修复前 exit 0）。
- 变更 deleteChange 后物理清行，再 `platform sync --change <名>` → 平台行收敛 location='deleted'。
- 本仓 daemon 无需重启：daemon 每次同步 spawn 新 sillyspec CLI 进程，全局 sillyspec 是源码仓 junction，修复对后续调用即时生效。
