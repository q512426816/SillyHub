# scan reopen 后 --done 把未执行步骤回填 completed

## 现象

`scan` 阶段（对其它带步骤阶段大概率同样成立）使用 `--reopen --from-step N` 回退重做后，任何一次 `--done` 都会输出：

```
⚠️ 同步回填 N 个 stale 步骤为 completed（reopen --from-step N 后 --done，方案未变）
```

把 **N 之后所有步骤（含从未执行过的）** 直接标记 completed，阶段宣告完成。

## 实测（2026-08-18 scan，两轮复现）

1. 第一轮：step 8 因等待用户决策期间状态被外部消费标完成（等待态丢失，`--continue` 报"没有处于等待状态的步骤"）；`--reopen --from-step 8` 做完模块卡片后 `--done` → step 9/10/11 未执行却被回填，阶段 11/11 完成。
2. 第二轮：`--reopen --from-step 9` 时进度显示被清零为 0/11（步骤 1-8 的 ✅ 全部丢失，虽然修订上下文声称"之前已完成的步骤仍然有效"）；补 8 个 `--done` 后做 step 9，`--done` → step 10/11 又被回填完成。

## 影响

- 未执行的步骤（知识提取、自检、git add 暂存）被状态机跳过，进度库与实际产物脱节；
- reopen 清零已完成步骤的显示，导致必须机械重走全部 `--done` 才能推进；
- `--wait` 暂停态可能被静默消费（第一轮的等待态在无 `--continue` 成功执行的情况下消失）。

## 绕过方案（当前）

- 每次 reopen 后机械补齐各步骤 `--done`（产物在盘上，post-check 可过），到目标步骤做真活；
- 完成后人工核对被"回填"的步骤是否真有产物（读 workflow prompt 源码 `src/stages/<stage>.js` 核对要求），缺的补做内容（本次 step 10/11 即如此补做）；
- 需要 `--wait` 用户决策时，决策后尽快 `--continue`，避免暂停态被并行会话/同步消费。

## 期望修复方向

- `--done` 只完成当前步骤，不回填后续步骤；后续步骤由真实执行推进；
- reopen 保留已完成步骤的 ✅ 显示与状态；
- 暂停态（waiting）应有显式消费记录（谁/何时/何答案）。
